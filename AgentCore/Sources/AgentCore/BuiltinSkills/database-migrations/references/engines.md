# Engine rules and migration tools

Read the section for your engine before writing DDL (SKILL.md step 1), and the tools table to find the status, up
and down commands.

## SQLite

- `ALTER TABLE` can only: rename a table, rename a column (3.25+), add a column, drop a column (3.35+; not if the
  column is indexed, in a constraint, a view or a trigger). Everything else (NOT NULL without a default, new
  CHECK or foreign key, type change, dropping a default) needs a **table rebuild**.
- `ADD COLUMN ... NOT NULL` needs a non-NULL default. If the request forbids a default, rebuild.
- Rebuild procedure (from SQLite's own docs):
  1. `PRAGMA foreign_keys = OFF;` **before** `BEGIN` (it is ignored inside a transaction). If the connection runs
     every script in a transaction you can't open, check how the runner calls the script.
  2. `BEGIN;` then `CREATE TABLE t_new (...)` with the new definition.
  3. `INSERT INTO t_new (cols) SELECT cols, <data rule> FROM t;`
  4. `DROP TABLE t;` then `ALTER TABLE t_new RENAME TO t;`
  5. Recreate the table's indexes, triggers and views (they are dropped with the old table).
  6. `PRAGMA foreign_key_check;` must return no rows; then `COMMIT;` and `PRAGMA foreign_keys = ON;`.
  With foreign keys ON, step 4's DROP deletes or nulls child rows through ON DELETE actions.
- Python's `sqlite3`: `executescript()` commits first and adds no transaction; `execute()` in the default mode opens
  transactions implicitly before DML.
- Inspect: `.schema t`, `PRAGMA table_info(t)`, `PRAGMA index_list(t)`, `PRAGMA foreign_key_list(t)`,
  `PRAGMA integrity_check`.

## PostgreSQL

- DDL is transactional, but takes locks: most `ALTER TABLE` forms take ACCESS EXCLUSIVE and queue behind running
  queries. Set `SET lock_timeout = '5s';` in the migration so it fails instead of blocking traffic.
- `ADD COLUMN ... DEFAULT <constant>` is fast (11+); a volatile default (`now()`, `gen_random_uuid()`) rewrites the
  table.
- NOT NULL on a big table: add `CHECK (col IS NOT NULL) NOT VALID`, `VALIDATE CONSTRAINT` (weaker lock), then
  `SET NOT NULL` (12+ uses the validated check and skips the scan), then drop the check.
- Foreign keys and checks: `ADD CONSTRAINT ... NOT VALID`, then `VALIDATE CONSTRAINT` in a separate step.
- Indexes: `CREATE INDEX CONCURRENTLY` (can't run in a transaction; most tools have a per-migration
  "no transaction" switch). A failed concurrent build leaves an INVALID index: drop it and retry.
- Type changes that rewrite (`int` → `bigint`, most `USING` conversions) lock and rewrite the table: use a new
  column plus backfill for large tables.
- Backfill in batches: `UPDATE t SET c = ... WHERE id BETWEEN $1 AND $2` committed per batch, outside the DDL.

## MySQL / MariaDB

- DDL is **not** transactional: each statement commits implicitly, so a failed migration leaves a half-applied
  schema. Keep one DDL statement per migration where possible, and make down handle partial states.
- Prefer `ALGORITHM=INSTANT` or `ALGORITHM=INPLACE, LOCK=NONE` and let the server refuse if it can't; large tables
  may need an online schema change tool (gh-ost, pt-online-schema-change) the team already uses.
- `ADD COLUMN ... NOT NULL` without a default fills existing rows with the type's implicit default (0, ''),
  silently: always state the backfill.

## Tools: status, up, down, new

| Tool | Status | Up | Down one step | New migration |
|---|---|---|---|---|
| Alembic | `alembic current`, `alembic history` | `alembic upgrade head` | `alembic downgrade -1` | `alembic revision -m "msg"` (`--autogenerate`: review it) |
| Django | `python manage.py showmigrations` | `python manage.py migrate` | `python manage.py migrate app <previous>` | `python manage.py makemigrations app` |
| Rails | `bin/rails db:migrate:status` | `bin/rails db:migrate` | `bin/rails db:rollback` | `bin/rails g migration Name` |
| Prisma | `npx prisma migrate status` | `npx prisma migrate deploy` (dev: `migrate dev`) | no down: write a new migration | `npx prisma migrate dev --create-only` |
| Knex | `npx knex migrate:status` | `npx knex migrate:latest` | `npx knex migrate:down` | `npx knex migrate:make name` |
| Flyway | `flyway info` | `flyway migrate` | `flyway undo` (paid) or a new migration | `V<n>__name.sql` file |
| goose | `goose status` | `goose up` | `goose down` | `goose create name sql` |
| sqlx / diesel | `sqlx migrate info` / `diesel migration list` | `sqlx migrate run` / `diesel migration run` | `sqlx migrate revert` / `diesel migration revert` | `sqlx migrate add -r name` / `diesel migration generate name` |

Autogenerated migrations (Alembic, Django, Prisma) often turn a rename into drop + add, which loses the column's
data: read the generated file and rewrite it as a rename.
