# kurtkode — plan

A native macOS chat app that works like Claude Code / Codex: an agent that reads, edits, and runs
commands in a project folder, backed by local models served by LM Studio (or any OpenAI-compatible
endpoint).

Build: `make test` (AgentCore unit tests), `make build`, `make run`, `make open` (opens Xcode).
The `.xcodeproj` is generated from `project.yml` by XcodeGen and is not checked in.

## Phase 0 findings (spike/)

`spike/toolcall_spike.py` probes the LM Studio API (stdlib Python; results in `spike/spike_results_*.json`).

API behavior (LM Studio, Gemma 4 26b-a4b MLX):
- Streaming deltas carry `content`, `reasoning_content` (separate reasoning channel), and `tool_calls`.
- With `stream_options.include_usage`, the final chunk has `usage` including
  `completion_tokens_details.reasoning_tokens`. Use it for the context meter.
- Tool calls are well-formed: valid JSON arguments, `finish_reason: "tool_calls"`, numeric-string ids.
  Streaming tool-call deltas assemble correctly by `index`.
- Gemma 4 reasons a lot even for trivial questions (~700 reasoning tokens, ~15 s to first content token).
  The UI needs a live "thinking" indicator; consider a reasoning-effort control if the API exposes one.

Agent-loop behavior (fake-filesystem task: find and fix a bug, 3 tools):

Variants: *base* prompt; *strict* prompt (results are above, don't repeat calls, read → edit, make
old_string unique); *framed* results (`[tool args]` header on each tool result); *both*.
Final runs: 20-step cap, `max_tokens` 4096, 180 s per-turn limit, 32k context, `--parallel 1` for
the models loaded by `run_matrix.sh`. Results in `spike/results/`, logs in `spike/logs/`.

| Model | Variant | Success | Median s | Tool calls | Tool errors |
|---|---|---|---|---|---|
| gemma-4-26b-a4b (MLX) | base, 10-step cap | 0/3 | — | hit cap | — |
| gemma-4-26b-a4b (MLX) | base | 4/4 | 34.4 | 6–10 | 2 |
| gemma-4-26b-a4b (MLX) | strict | 4/4 | ~28 | 6–13 | 1 |
| gemma-4-26b-a4b (MLX) | framed | 4/4 | ~35 | 6–10 | 3 |
| gemma-4-26b-a4b (MLX) | both | 4/4 | 27.9 | 6–9 | 2 |
| gemma-4-12b (GGUF) | strict | 4/4 | 14.3 | 5–7 | 1 |
| gemma-4-e4b (GGUF) | strict | 4/4 | 45.5 | 5–9 | 7 (one run took 132 s) |
| **qwen3-coder-30b-a3b (MLX)** | base | 4/4 | 10.4 | 4–6 | 0 |
| **qwen3-coder-30b-a3b (MLX)** | strict | 4/4 | 9.0 | 3–6 | 0 |
| **qwen3-coder-30b-a3b (MLX)** | both | 4/4 | 10.1 | 5–6 | 0 |

(The first strict and framed runs of the 26b had no `max_tokens` or turn limit. An earlier "both" run
without them hung; see below.)

Takeaways for the agent design:
- **The 0/3 was the 10-step cap, not the prompt.** Base at 20 steps succeeds 4/4. Default step cap
  should be generous (≥ 25) with a UI "continue" when hit, not a hard failure.
- **Qwen3-Coder 30B is the best default** for kurtkode: ~3× faster than Gemma 26b, fewest calls,
  zero tool errors, and no separate reasoning stream (0 reasoning tokens). Gemma 4 spends ~200–700
  reasoning tokens even on trivial prompts. The 12b is the best Gemma for speed.
- Prompt and framing variants made little difference on this easy task. Keep the strict wording in
  `SystemPromptBuilder` (it's cheap), make it tunable per model, and re-test on harder tasks.
- D5 settled: native tool calls work for every model tested; no text-protocol fallback needed.
- Detect repeated identical tool calls and inject a nudge ("you already called X with these arguments;
  the result is above") rather than executing them again.
- `edit_file` uniqueness errors are common; the error text must say how to fix it (add context lines).
- **Runaway generation is real.** One turn deep in an agent run (22 messages) generated for 78 minutes
  with no end, because the request set no `max_tokens` and the model had a 262k context. Every request
  must set `max_tokens`. The loop also needs a per-turn wall-clock limit and repetition detection on the
  streamed text, and the UI needs a visible "still generating: N tokens, M s" status with Stop.
  Closing the HTTP connection does stop LM Studio ("Client disconnected. Stopping generation..."),
  so cancelling the Swift task is enough to abort.

LM Studio quirks:
- LM Studio listens on **127.0.0.1 only**. `localhost` resolves to `::1` first and gets refused, so the
  default endpoint is `http://127.0.0.1:1234`.
- Just-in-time loading uses a small default context (the 12b came up at 8192 of 262144) and unloads
  after an idle TTL. Hence D12: kurtkode loads models itself with an explicit context length.
- `lms load --identifier X` makes the instance appear in `/api/v0/models` as a separate entry `X`
  while the original id reports `not-loaded`. kurtkode should load under the model's own id.
- `lms load --context-length 32768` on the MLX 26b build still reports `loaded_context_length` 262144.
  Treat the reported value with suspicion for MLX models; verify in Phase 1.
- `lms load` prints an animated progress bar; redirect or strip `\r` when running it from the app.
- **Memory.** `lms load` defaults to 4 parallel slots, each with its own cache: the 12b's
  llama-server grew from 10 to 15 GB (7 GB of weights). With the MLX 26b also loaded, free RAM hit
  0.1 GB and swap was nearly full. MLX model memory doesn't show in per-process RSS, so read
  system-wide numbers (`memory_pressure`, `vm.swapusage`). kurtkode must: load with `--parallel 1`
  by default, unload other models first unless asked not to, show free RAM next to the model picker,
  and estimate weights + cache for the chosen context before loading, warning when it won't fit.
  Qwen3-Coder 30B at 32k context with 1 slot used about 11% of RAM.
- `lms get NAME -y` takes the first staff pick when a name is ambiguous. Confirm the resolved repo
  (it's in `~/.cache/lm-studio/.internal/single-downloads-info.json`) before assuming.

## Phase 1 findings

- **LM Studio substitutes models silently.** A request for a model id that doesn't exist got no
  error; whichever model was loaded answered. kurtkode records the `model` field of the stream and
  warns under the reply when it differs from the requested one.
- LM Studio's error body is `{"error": "text"}`, not OpenAI's `{"error": {"message": ...}}`. The
  client reads both, plus plain text.
- Loading gemma-4-12b (7 GB file, 16k context, 1 slot) took free memory from 82% to 40%, and it only
  came back to 52% after unloading. File size is a poor predictor, so the app measures free memory
  before and after each load and reports the difference.
- `URLSession.AsyncBytes.lines` drops blank lines, so SSE parsing treats each `data:` line as one
  event (true for OpenAI-compatible servers).
- UI scripting (System Events keystrokes) is blocked without Accessibility permission. For
  end-to-end checks, debug builds accept `open --env KURTKODE_AUTOSEND="text" kurtkode.app`, which
  starts a chat and sends the text; `screencapture -l <window id>` works for screenshots.
- No code-signing identity on this Mac, so builds are ad-hoc signed. Keychain items (endpoint API
  keys) will prompt for access after each rebuild. A free Apple Development certificate
  (Xcode → Settings → Accounts) would stop that.

## Phase 2 findings

Real runs with Qwen3-Coder 30B on this repo (32k context):

| Question | Tool calls | Context used | Result |
|---|---|---|---|
| "Explain how this repo is organized" | 15 | 12.6k | Accurate structure and data flow |
| "Where is the repetition detector…? Cite file and line." (first prompt) | 11 | ~6k | Correct, line numbers exact |
| same question, after rewording the prompt | 3 | ~5k | Same answer |
| "Which tools can the agent use…? Short table." | 7 | 10.1k | Correct table |

- **Prompt wording steers the first move.** "Start broad (list_dir, glob)" made the model list
  directories and guess file names before searching. Saying "to find where something is defined,
  grep first; to understand layout, start with list_dir" cut a lookup from 11 calls to 3.
- Line-numbered `read_file` output lets the model cite exact lines.
- Qwen often calls several tools in one turn and narrates between calls ("Let me look at…"). The
  narration is kept as message text above the tool cards.
- A 12k-token repo overview fits in 32k, but a long session won't: Phase 4's truncation and
  compaction matter.
- The transcript's bottom-follow must key off the user's scroll phase. Geometry changes from
  content growth made `onScrollGeometryChange` think the user had scrolled away.

## Phase 3 findings

Exit test: a two-bug Python project (`sub` used `+`; `mean` divided by `len - 1`), Ask mode, Qwen3-Coder.
The agent listed, read both files, ran the tests (exit 1), fixed both bugs in one edit, re-ran (exit 0)
and summarized with line numbers: 7 tool calls, 3 approvals (bash, edit, bash), ~3k context. Rewinding
restored `calc.py` and removed the 14 messages; only `__pycache__/` (made by a command) remained.
Asked to "run the tests and don't change anything", it ran and read but made no edits.

Design notes:
- Approval previews are computed before asking; a call that can't succeed (old_string not found,
  path outside the project) returns its error to the model without bothering the user.
- Deny without feedback stops the run and the rest of that turn's calls; deny with feedback
  continues and the model sees the text.
- Command allow rules match only simple commands: any of `; & | ` $( > < newline` needs asking.
  Suggested rules are narrow ("git status", "python3 -m unittest"), never a bare interpreter.
- bash runs in its own process group (posix_spawn); timeout and Stop kill the group, including
  background grandchildren. stdin is /dev/null; PAGER/GIT_PAGER=cat, TERM=dumb.
- `zsh -l` loads ~/.zprofile but not ~/.zshrc. Tools set up only in .zshrc (some pyenv installs)
  won't be on PATH. Revisit if that bites.
- The repeat-call nudge applies only to read tools, and resets after any edit or command.
- UI: content in a two-way ScrollView sizes to fit and centers; `CodeScroll` pins it left at full
  width. Auto-follow scrolls one layout pass later so new cards are measured. A button with a Return
  shortcut is drawn as the default button, so "Always allow" uses ⌥⌘A instead.

## Phase 4 findings

Exit test: document all 25 Swift files of a copy of AgentCore (155 KB) in FILES.md with each file's
first public type (checkable), Qwen3-Coder 30B, 32k context, Full Auto. Compaction triggers at about
14.7k prompt tokens (70% of 32k minus 8k reserved for output).

| Run | Change before it | Result | Calls | Compactions | Peak prompt |
|---|---|---|---|---|---|
| 1 | first build | paused at the 30-step limit, 10 files | 30 | 2 | 14.4k |
| 2 | step limit 100; summary must have "## Summary" | paused at 100 steps, 14 files: half its FILES.md edits failed | 100 | 5 | 14.8k |
| 3 | write_file append; edit errors show the file's end | done in 33 s having read nothing: descriptions guessed from names | 11 | 0 | 3.5k |
| 4 | task asks for a checkable fact (first public type) | guessed again: 15 of 23 wrong | 12 | 0 | 4.6k |
| 5 | system prompt: never describe a file you haven't read | read files, but after compactions re-did the middle and never reached the end: 19 files, 10 duplicates | 87 | 8 | 14.7k |
| 6 | kurtkode tracks progress facts and puts them in every compaction | **done: 25/25, no duplicates or re-reads, 0 tool errors**; 19/23 types right (4 named the main type, not the first); 1 made-up line for a nonexistent file | 40 | 5 | 14.5k |

What each run taught:
- **The prompt cache dominates latency.** Re-processing a 24k-token prompt took 122 s; the same prompt
  from the cache took 0.5 s. So: the system prompt is built once per session and mode and never
  changes; the summary is appended to it the same way in-run and in later runs; context is reduced
  only in rare large steps; the summary request reuses the exact prompt plus one instruction.
- **Summaries from the model aren't enough to carry progress.** They drift ("I've been systematically
  reading each file") and the model redoes work. kurtkode now tracks progress itself from the tool
  history (files read, files changed with edit counts, the todo list) and adds it to every compaction.
  That, not prompt wording, fixed the looping.
- **A model mid-task sometimes keeps working instead of summarizing.** The instruction asks for a
  "## Summary" heading; without one, the no-tools transcript fallback runs (slower, reliable).
  Structural check only, no wording heuristics.
- **Appending with edit_file fails half the time.** The model uses the last line as it remembers it.
  write_file now has `append`, and a failed match shows the file's current last lines.
- **Models take shortcuts on big tasks** (runs 3 and 4 wrote plausible descriptions from file names), and
  one made up a line for a file that doesn't exist. The system prompt forbids describing unread files;
  the eval suite must check content against ground truth, not just "the file exists".
- The overflow error is recognized ("tokens to keep … greater than the context length"): compact once, retry.
- Step limit is a setting (default 100). The per-turn limits, repetition detection and Stop are the guards.

Other findings:
- **MLX memory is taken during inference, not at load** (free memory 83% → 82% at load), and grows as the
  MLX buffer cache fills: 36 GB wired for a 17 GB model late in a long run, down to 23% free. Reloading
  the model releases it. So a profile's measured footprint must be the peak in use, and the app should
  offer a reload when an idle model has grown well past it.
- **Keychain reads can block on a macOS permission dialog** after every rebuild of an ad-hoc-signed app;
  on the main thread that froze the UI. Reads now happen off the main thread, and model lists are fetched
  without the key (retrying with it only on 401/403). A stable signing identity would stop the dialogs.
- People paste full request URLs (`…/v1/chat/completions`) as the base URL; endpoints now normalize it.
- Deleted files stay on disk while local Time Machine snapshots hold them (not an app issue).

## Architecture

```
AgentCore/            Swift package — no UI
  LLM/                ChatClient (SSE), WireFormat, TurnRunner (limits: max_tokens, wall clock,
                      repetition), TurnAccumulator (tool-call delta assembly), message/tool types
  LMStudio/           LMStudioService (/api/v0 metadata), LMSCLI (server start, load/unload, ls), MemoryStatus
  Endpoints/          Endpoint + EndpointStore (JSON), KeychainStore (API keys)
  Agent/              AgentLoop (repeat-call nudge, step limit), SystemPromptBuilder; later ContextManager, Compactor
  Tools/              Tool protocol, Workspace (path confinement, git ls-files), Glob; read_file, list_dir, glob,
                      grep (Phase 2); edit_file, write_file, bash, todo_write (Phase 3–4)
  Permissions/        Mode (ask / acceptEdits / plan / fullAuto), rules, async approval requests
  Session/            JSONL store, checkpoints (pre-edit snapshots per turn)
App/                  SwiftUI: AppModel (shared), ChatController (per session), views; Textual for Markdown
spike/                Phase 0 API probes
```

Agent loop: build messages (system prompt + instructions + env) → stream completion → for each tool
call, check permission (awaiting a UI approval if needed) → run → trim result → append → repeat until
no tool calls or the step cap. Cancellation kills the tool's process group.

## Phase 4.5: model profiles, multi-model sessions, eval suite

Goal: several models, from different sources (LM Studio here, other OpenAI-compatible servers), in one
session, with no model-specific code paths. Everything that differs by model is data in a profile, and
every tuning decision is checked across models by a repeatable eval.

**Model profiles** (`ModelProfile`, keyed by endpoint + model id). Defaults come from what the server
reports; the user can override them in Settings.
- `contextLength` to load with, and the budget that compaction uses
- `maxOutputTokens`, `temperature`
- `reasoning`: whether the model emits reasoning, shown collapsed; never sent back
- `supportsTools` (from LM Studio `capabilities`, or manual for other servers)
- `promptAddendum`: optional text appended to the system prompt for this model
- History shaping for chat templates: `toolCallIDStyle` (as-is, or 9-character alphanumeric for
  Mistral-family templates), `strictAlternation` (merge or bridge consecutive same-role messages)
- `measuredMemoryBytes`: learned from free-memory deltas at load (file size is a poor predictor)

**Multi-model sessions**
- The model (endpoint + id) is chosen per turn; each assistant message records both. The session's
  current model is just the default for the next turn.
- Roles, each with its own model: `main` (the agent) and `summarizer` (compaction). Later: subagents.
- On a switch: the budget and token calibration follow the new model (compact at once if the history
  won't fit); tool-call ids and roles are reshaped for its template; the UI says the first reply
  re-processes the whole prompt (no cache across models).
- Memory-aware loading for local models (64 GB machine): keep several loaded when the measured
  footprints plus a 25% free-memory margin fit, otherwise unload the least recently used; never load
  when free memory is under 30%. Always `--parallel 1` and an explicit context.

**Eval suite** (`kurtkode-eval`, a command-line target on AgentCore; runs headless)
- Scenarios, each with a fixture project and an automatic check:
  1. `explain-repo`: answer mentions the real top-level parts (checked against a key list)
  2. `find-definition`: cites the right file and line
  3. `fix-tests`: tests go from failing to passing; no other files changed
  4. `long-doc`: FILES.md lists every source file; compaction happened; context never overflowed
  5. `deny-feedback`: follows feedback after a denied edit
  6. `model-switch`: starts on model A, switches to B mid-task, finishes
- Runs N trials per model; reports success, steps, tool errors, compactions, time, peak prompt size.
- Models are loaded one at a time (or in fitting pairs for `model-switch`), with the free-memory guard.
- Results are saved as JSON with the git commit, so prompt changes can be compared across models.

What the failures showed, and the general fixes (none specific to a model):
- **Qwen batched 14 reads in one turn**, more output than the whole (capped) budget; compaction couldn't
  keep them, compacted three times in a row, and the model wrote "No class found" for every file.
  Fixes: a per-turn tool-output budget (35% of context; later calls in the turn are refused with advice
  to work in smaller steps), and no repeated compaction when the last one didn't get under the threshold
  (trim tool outputs harder instead).
- **Devstral's template requires strict user/assistant alternation** except for tool calls and results.
  The cache-reusing summary request (a user message right after a tool result) failed on 4 of 5
  compactions, and one regular turn failed the same way. Fix: `HistoryShape.mergeConsecutive` now also
  bridges tool → user with a short assistant turn; on by default for the Mistral and Gemma families.
- **Devstral sometimes writes tool calls as text** (`[TOOL_CALLS]edit_file {…}`) that LM Studio doesn't
  convert. Fix: `parseTextToolCalls` recovers Mistral and Hermes-style text calls (known tool names and
  valid JSON only); on for the Mistral family. (This is the D5 fallback, now justified by data.)
- LM Studio already emits 9-digit tool-call ids, which Mistral templates accept; the id reshaping
  matters when history comes from another source (e.g. OpenRouter's `call_…` ids) in a mixed session.
- Speed differs a lot: Devstral (24B dense) took 581 s for a read-only overview Qwen (3B active) did in 35 s.

**Built so far**: `ModelProfile` + `ProfileStore` + family table; `HistoryShaper`; text tool-call
recovery; per-turn endpoint in sessions (`.model` records carry the endpoint); assistant messages record
their endpoint; model menu across endpoints with a searchable browser; per-model profile editor;
switch notice (the new model re-reads the whole conversation); memory-aware loading (keep models that
fit with 25% free, else unload least recently used; learn each model's peak footprint while it runs);
optional summarizer model.

What the remote runs found, and the general fixes:
- **No retry on transient errors.** Now `ChatClient` retries 408/429/502/503/504 (2, 5, 10, 20, 30 s, or
  Retry-After up to 60 s) before any byte is streamed. A plain 500 isn't retried (on LM Studio it's a
  template error).
- **An empty reply was taken as "done".** Remote Qwen grepped `func reserve_stock` in a Python project,
  found nothing, and ended with no text. Now the loop asks again (up to 3 times per run), and the empty
  turn isn't sent back. The nudge says what most likely happened: a call written into the reasoning, or
  output tokens with nothing delivered (the server dropped a call it couldn't parse).
- **Qwen3-Coder's XML calls arrived as text** from one provider (`<function=grep><parameter=pattern>…`,
  opening `<tool_call>` missing). `TextToolCalls` now parses that format, typing values by each tool's
  schema (strings verbatim); on by default for the Qwen family. Recovered arguments encode with sorted keys.
- **gpt-oss wrote its tool call into the reasoning** (`"Let's list inventory.{"path": "inventory"}"`, no
  name) and returned nothing. The repeated nudge fixed it (3/3 with and without profiles). New profile
  option `sendReasoning` (on for the gpt-oss family) sends reasoning back with each assistant turn:
  2 empty turns in 3 trials vs 4 without, 46 s vs 94 s mean. A small sample; keep it on, re-measure later.
- **Provider-side parse failures are the main remote risk, and nothing on the client can recover them.**
  Qwen 30B once made 10 `read_file {}` calls (arguments lost by the provider), and on long-doc it returned
  4 empty turns in a row, each reporting 25–72 output tokens: its FILES.md write was dropped every time.
  The same model locally scored 0.93, and continuing a local start remotely scored 1.00. The tailored
  "your call was dropped" nudge was written after these runs. **A re-run (2 trials, $0.15) didn't exercise
  it**: no calls were dropped that time, and Qwen scored 0.57 and 0.93 (8/14 and 13/14). So the earlier
  0/2 was the provider on that run, not the model.
- **Nudge wording can't recover dropped calls (measured).** `spike/fault_proxy.py` sits between the eval and
  local Qwen3-Coder and drops write_file/edit_file calls with more than 300 argument bytes, returning an
  empty reply that still reports its tokens (as the provider did). long-doc, 3 trials per arm
  (`eval-results/nudge-ab-*`, `run-nudge-ab-2026-09-27.sh`):

  | Nudge after a dropped call | Passes | Mean score | Drops |
  |---|---|---|---|
  | generic: "Your last reply was empty. Continue the task…" | 0/3 | 0.07 | 12 |
  | v1: "the server dropped your call; don't repeat it as it was" | 0/3 | 0.05 | 12 |
  | v2: v1 + "keep its arguments under about N characters; write_file with append" + 3 in a row, not per run | 0/3 | 0.10 | 13 |

  After every nudge the model sent nearly the same call again (386, 386, 386, 386 bytes). It can't see the
  lost call, and a user message barely changes what it generates next; it never switched to append. The
  fix has to be structural: send the retry somewhere else (another OpenRouter provider, using the
  `provider` field of the reply and the request's `provider.ignore`, or another model in the session).
  v2 is kept: its wording is harmless, and counting nudges in a row (not per run) is right for long tasks. OpenRouter
  can pin providers per request; that would be an endpoint-level profile option (not built).
- Reported cost ran up to 4× the listed price for Qwen 30B (the router picked a pricier provider).
- The eval records tokens and cost per trial, reads OpenRouter's key usage between trials, and stops
  starting trials at `--max-cost`. Every release rebuild changes the ad-hoc signature, so macOS asks
  again for the Keychain key; chain paid runs in one script against one binary.

## Compactions that don't shrink the prompt (2026-10-11, fifth session)

Found with the Journal (above): in the 9k Gemma run the first compaction summarized only the user's opening message
and the prompt grew, 4,418 → 5,126 tokens. The cause: the kept part was sized as 20% of the *limit* (1,800 tokens),
but the system prompt and tool schemas took about two thirds of the prompt, so when the threshold (4,050) was
passed the whole body (about 1,500 tokens) fit in the keep budget. The cut kept all of it and summarized the one
message before it, and a 400-word summary plus tracked progress is far bigger than a one-line request. The three
compactions after it shrank the prompt only to about 4,800, still over the threshold.
- **`Compactor.plan`** works out a compaction before asking for a summary: the fixed part (base system prompt, tool
  schemas, room for the summary: 2.6 KB or the last summary's size if larger, and the tracked progress), the kept
  part sized at most half of what the threshold leaves after the fixed part (and never more than the keep
  fraction), the cut, and the predicted prompt afterwards.
- **A compaction must save a tenth of the limit** (`minimumSaving`), or it doesn't run: no summary request, no cold
  cache. Instead the loop trims tool outputs the model has already answered to 1.2 KB (`trimAnswered`; the newest
  results reach the model whole: the old fallback trimmed them too, before the model saw them). The next reply
  carries a note ("Didn't compact: a summary would leave about X of Y tokens…"), once until a compaction happens.
  After the summary comes back the result is checked again; a summary longer than planned is dropped.
- On a context-overflow error any saving counts (`minimumSaving: 1`); failing that, trimming answered outputs and
  retrying once.
- Trimming is now stable: a message already trimmed to a size is left alone at that size (the truncation note
  pushed it over, so each step re-trimmed it, added a newline, and broke the prompt cache from there on).
- The old "don't re-compact right after a compaction" rule is gone: the plan covers it (re-summarizing a body of
  continuation + newest step only swaps one summary for another, and the plan says so).
- Tests: the session-4 shape as a plan (summarizes more than the opening message, and still declines), a loop run
  where both steps decline (no summary request, the answered read trimmed, the new one whole, one note), stable
  trimming, a re-compaction declined. The older compaction tests used 3–4k budgets where compacting genuinely
  couldn't help (the newest step, one big read, is always kept); they now read two files at a 12k budget.
- **Summaries cut off by reasoning.** Watching a real run found 67 s lost per failed compaction: Gemma 4 26B spent the
  whole 1,500-token summary cap thinking, twice (the cached request, then the plain-transcript fallback; LM Studio's
  log showed both at ~33 s), so no summary came back and nothing recorded why. A summary now gets as much output as
  the context leaves after the prompt, 1,500 to 4,000 tokens (`summaryMaxTokens`), and a failed one leaves a note
  ("Didn't compact: no usable summary came back…"). `/compact` still uses 1,500 (it has no context size at hand).
- **Measured** (the 8-file task from the Journal check, kurtkode CLI, Gemma 4 26B as the user had it loaded: 8k
  context, so threshold 3,686; each file read is ~2.4k tokens, the CLI's system prompt and tools ~1.8k; one trial
  each; the user's own app was using the same Gemma instance during the runs, so times are only rough):

  | Build | Compactions | Grew the prompt | Lost summaries | NOTES.md | Time |
  |---|---|---|---|---|---|
  | before (8da970c) | 2 | 1 (4,420 → 4,466) | 0 | 4 of 8; then said "processed all files" | 2.9 min |
  | planned compactions | 7 | 0 (e.g. 4,462 → 2,957) | 2 (67 s) | 8 attempted, 7 right; garbled at the end | 13.0 min |
  | + summary room | 8 | 0 (5,385 → 3,187 at most) | 0 | 7 of 8 right (part6 missing) | 13.6 min |

  At 8k every file read crosses the threshold, so the steady state is one compaction per file: the step after a
  read declines (the read is the newest step, always kept) and the next one compacts. Each summary costs Gemma
  ~60–90 s of thinking. Ways to shorten that: a larger loaded context, a summarizer model, or (not checked yet)
  turning reasoning off for the summary request.

  it has no cache to lose, and it's mostly reached when thinking used up the output room. The eval follows the
  default; `KURTKODE_SUMMARY_THINKING=0` turns thinking off.

## Compaction leftovers (2026-10-11)

- **`/compact` sizes its summary from the context** (`compactAll(contextLimit:)`; the app and CLI pass the session's
  context size): 1,500 to 4,000 tokens, as in the loop; 1,500 when the size isn't known.
- **The eval keeps each summary**: `TrialResult.summaries` (tokens before/after, how long the summary took, its text)
  and `compactionsSkipped` (the "Didn't compact" notes); the log line shows the summary's time and size.
- **Small contexts: no later compaction point.** Considered compacting later when the system prompt and tools are
  most of a small context (the 8k runs compact once per 2.4k-token read). It would make overflows likelier: one
  turn's tool output may be 35% of the context, so at 8k a prompt just under today's threshold (3,686) plus a
  full turn of output (2,867) plus the reply room (2,048) is already ~8.6k of 8,192. The overflow path catches that
  (compact with any saving, else trim), but a later threshold would hit it routinely. The remedy at 8k is a larger
  loaded context: at 64k the 8-file task doesn't compact at all.
- **More `long-doc` trials, thinking on and off** (Gemma 4 26B at 64k, 3 more trials each; with the first two runs,
  4 per side):

  | Summaries | Passed | Run times (s) | Compactions | Each summary | Summary size (median) |
  |---|---|---|---|---|---|
  | thinking on | 4 of 4 | 183, 300, 549, 662 | 2–6 | 11–55 s (median 39) | 1.4 KB |
  | thinking off | 3 of 4 | 199, 346, 396, 593 | 2–6 | 24–31 s (median 26) | 1.5 KB |

  The 2× from the first pair was chance: run times swing 3× either way, driven by how many compactions a run
  happens to need. Thinking off makes each summary steadier; summaries are the same size. The one failure stopped
  on an agent reply cut off at the output limit (not a summary). The default stays on.

## Subagent management, phase 4: parallel subagents (2026-10-12)

- **In the loop**: when one reply has two or more `task` calls, each starts in the background as soon as it's
  authorized and the other calls go on; every result of that turn is emitted after the last call, in call order
  (the model sees them in order). Each parallel task's report gets an equal share of the turn's remaining output
  budget. A main Stop cancels them all; a denial later in the turn cancels them too. Results carry the note
  "Ran in parallel with the turn's other subagent tasks." One `task` call per reply behaves as before.
- **Limits** (`SubagentSetup.slots`, `SubagentLimiter`): runs on one endpoint and model share its slots: on this Mac's
  LM Studio the loaded model's parallel slots (`lms ps --json`, new `LMSCLI.loadedModels()`; 1 if not listed),
  elsewhere Settings → Generation → Subagents "At once on other servers" (default 4, `RunSettings.subagentParallel`).
  Runs whose tools can change things (any tool that isn't read-only) also go one at a time among themselves (the
  user's decision). A run beyond a limit waits, shown as "Waiting for a free slot" (`SubagentProgress.waitingForSlot`),
  and can be stopped while it waits.
- **App**: approvals are a queue (`ChatController.approvals`; a stopped asker's request is withdrawn as "deny");
  several task cards can show running at once (`runningTools`); the Debug window finds every running task's run.
- **CLI**: approval prompts take turns (`PromptTurns`), so two parallel askers can't interleave in the terminal.
- Tests (`ParallelSubagentTests`, 3): read-only runs on two models overlap and keep call order (the model's next
  request too); two writers go one at a time; a model with one slot takes one run at a time. A first version of the
  tests was flaky because two subagents' events arrive at once; the tests now record under one lock (10/10 runs).
- Checked on Gemma 4 26B (64k, 1 slot): asked for two explore tasks in one reply, Gemma made both calls; one ran,

## Subagent management, phase 5: background subagents (2026-10-12)

- `task` takes `background: true`. The call returns at once ("Started the explore subagent in the background (…).
  Its report will arrive as a message…"), linked to its run, and the run goes on in a task of the main loop's
  (`BackgroundRuns`). Only agents whose offered tools are all read-only may run in the background (decided here,
  not in the design: a writer would change files under the main agent's feet); others get an error saying to run
  without background. Its live step lines go to the Agents list, not the finished card.
- **Delivery**: a finished run's report is added before the next request, through the same path as queued input,
  as a user message marked `ChatMessage.subagentReport` (the run id) that begins "[Report from the explore subagent
  you started in the background: "…". This is its final report, not a message from the user.]".
- **The loop doesn't finish while background runs go**: where it would stop, it emits `.status("Waiting for N
  background subagent(s) to report…")`, waits for the next report, and goes on with it. Every way out of the loop
  (Stop, step limit, denial) stops the runs still going (`defer`); a run stopped alone still reports.
- **App**: a delivered report shows as its own card ("Report from the scout subagent: …", the report without the
  delivery line and closing note, Open in Debug), not as a user bubble; the status shows as the notice. **CLI**: a
  status line and "⤶ a background subagent reported"; stream-json `status` and `subagent_report`.
- Prompt: the task tool's description says when to use background and not to wait or poll.
- Tests (`BackgroundSubagentTests`, 3): the report arrives as a marked message after the main agent's interim
  reply and the loop waits for it (status event, final answer from the report, the model sees it in order); a
  writer can't go to the background; stopping the main agent while it waits stops the background run.

## Native Anthropic and Gemini APIs (2026-10-13, eighth session)

Claude and Gemini are spoken natively, not through their OpenAI-compatible endpoints, because those lose what matters
for this app: the reasoning (summarized thinking, thought summaries) and the opaque state that must go back verbatim
(Anthropic thinking blocks with signatures; Gemini thought signatures, which Gemini 3 requires on function calls or
answers 400).

- **Endpoints**: `Endpoint.Kind` gains `.anthropic` and `.gemini` (presets "Anthropic" `https://api.anthropic.com/v1`,
  "Google Gemini" `https://generativelanguage.googleapis.com/v1beta`). Saved as `kind: "openai"` plus `api`, so an older
  build reads them as OpenAI-compatible instead of failing to read the whole list (and then overwriting it). A
  one-run `--endpoint` on either host gets the native kind (`Endpoint.detectedKind`; Google's `…/openai` path stays
  OpenAI-compatible). The CLI and eval also read `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`/`GOOGLE_API_KEY` after
  `KURTKODE_API_KEY_<NAME>`.
- **One boundary**: `ChatClient` has an `api` (`WireAPI`); it picks the path (`messages`;
  `models/{model}:streamGenerateContent?alt=sse`), headers (`x-api-key` + `anthropic-version` + `anthropic-beta` derived
  from the body; `x-goog-api-key`), encoder and a stateful `StreamDecoder`. Everything above it still sees
  `StreamEvent`s; new ones: `.note` (refusal, fallback, dropped thinking → `meta.notes`), `.discardToolCalls`, `.native`.
- **Round-tripping**: each reply's content as returned is kept on the message (`ChatMessage.native`: api, model,
  blocks). It goes back verbatim while the message still matches it (text, tool call ids/names/arguments: the loop can
  rename or recover calls) and the same model is asked; otherwise it's rebuilt from text and calls — for Anthropic
  without thinking, for Gemini with `skip_thought_signature_validator` on each step's first call (Google's documented
  stand-in). Gemini's streamed text parts are merged per run, signatures kept on their part.
- **Anthropic requests**: system prompt top-level; tool results as `tool_result` blocks merged into one user message;
  ids mapped to `[A-Za-z0-9_-]`; history starts and ends on a user message (no prefill on new models); top-level
  `cache_control` (automatic prompt caching). By generation (`AnthropicWire.generation`): Claude ≤4.5 thinking only with
  a budget from `reasoning_effort` and sampling allowed; 4.6 adaptive (or disabled for "none"); 4.7 and later adaptive

  be turned off), no temperature (400 there), and `block_binding: drop_block` (beta `thinking-binding-controls-2026-08-01`):
  kurtkode rewrites history (compaction, trimmed outputs), which on accounts created after 2026-08-31 makes a replayed

  Opus 5/5.5, Sonnet 5.5, Fable 5.1 also send `fallbacks: "default"` (beta `server-side-fallback-2026-07-01`): a declined

  `thinkingBudget` (2.x). Usage: completion = candidates + thoughts; reasoning = `thoughtsTokenCount`.
- **Context**: both list models with context lengths (Settings' catalog, the CLI); a session uses at most

- **Debug**: `WireRecord.api` (from the URL), `messages` with the native system prompt first; images' base64 left out

### Closed-model fixes: declined replies, spending limits, output limits (2026-10-14)

1. **Declined replies aren't lost replies.** `TurnMeta.declined` (stream event `.declined`): a Claude refusal, a Gemini
   safety stop or blocked prompt (`GeminiStreamDecoder.declinedReasons`), OpenAI's `content_filter`. A declined reply
   isn't retried on another provider or the fallback model, isn't nudged (empty or open-todos), and ends the run with
   the server's note. `AgentLoop.droppedCall` also subtracts billed thinking (`Usage.reasoningTokens`) rather than the
   shown summary's size: a Claude reply with 1,995 thinking tokens and a short summary isn't "lost".
2. **Spending limits.** `CostMeter` (shared by a run, its summaries, and its subagents via the copied config) adds each
   reply's cost; the loop pauses before its next request once a limit is reached (`AgentStop.costLimit`): per run
   (Settings → Generation → Spending, default $2.00; Continue allows another run's worth) and per session (default
   off; counts earlier replies and, with a limit set, the session's subagent runs). The main window's toolbar shows
   what the session spent ("≈$0.028"; subagents included, live via `SubagentProgress.cost`); a banner on the stop;
   the CLI says so (`cost_limit` in JSON). Costs are reported (OpenRouter) or list price (Claude, Gemini); models
   without a price count nothing.
3. **Output and time limits for Claude and Gemini**: `RunSettings.nativeMaxTokens` 32,768 and `nativeWallClock` 30 min
   (Settings → Generation → "Limits for Claude and Gemini replies"; a profile's output limit wins), used when the
   endpoint speaks a native API (`SessionRun(api:)`), for subagents on such a model (`AgentConfig.nativeLimits`), and
   summaries there get at least 16,000 output tokens (thinking counts). 266 tests; a Gemma run through the CLI checked.

### Switching costs and privacy (2026-10-14)

3. **The cost of switching models.** Caches belong to one model, and Claude's thinking only goes back to the model that
   wrote it: a large session switched to another model resends everything uncached. `PriceList.switchCost` (the
   prompt at input price, as a cache write on Anthropic) and `switchNote`; the model menu shows "≈$0.48 to switch" for
   priced models once the session holds 8k+ tokens; after a switch the app's notice and the CLI's `/model` say how much
   is resent, that switching back costs as much again, and that Claude's thinking stays behind.
5. **Privacy with remote models.** `Endpoint.isThirdParty` (Anthropic, Google, and any host outside this Mac and the
   private network; LAN, `.local`, Tailscale's 100.64/10 are not). Settings → Generation → Privacy lists file patterns
   (`WithheldFiles.defaults`: `.env`, `.env.*`, keys, certificates, `.netrc`, credentials…; templates like
   `.env.example` allowed; slash patterns match the path's end). For a run on a third-party model the loop sets
   `Workspace.withheld`: resolving such a path fails with a clear message (read, edit, write), and grep skips them
   with a count. Commands aren't filtered (said in Settings), and @-attachments are the user's choice. The model
   button shows a cloud for remote models, with a tooltip; the Gemini preset warns about the free tier. 269 tests;
   a Gemma run (local: `.env` readable) checked.

### Rate limits, web search, and a lean prompt (2026-10-14)

8. **Rate limits and retired models.** `RateLimits` (an actor shared by all clients, per host) reads Anthropic's
   `anthropic-ratelimit-{requests,input-tokens,tokens}-{remaining,reset}` from every response; a request waits for
   the reset (at most a minute) when a window is used up (requests 0, or under 1,000 tokens left), so parallel
   subagents on one Claude model pace themselves instead of collecting 429s. A 429 without Retry-After uses Google's
   `retryDelay` from the error body. A 404 adds: the server doesn't offer the model (retired, renamed, not enabled for
   the key) or the URL is wrong; pick another, Refresh Models lists what it offers.
7. **Web search** (Settings → Generation → Web search, off by default): Claude gets Anthropic's server tool
   (`web_search_20260209` on Opus 4.6+/Sonnet 4.6+/5.x, else `web_search_20250305`; `max_uses` 5), Gemini Google Search
   grounding (`googleSearch`). Claude's `server_tool_use` blocks aren't calls for kurtkode (their streamed input no
   longer becomes a tool call); search results (encrypted content) and text citations (`citations_delta`) are kept in
   the native blocks and sent back as returned. `Usage.webSearches` from `usage.server_tool_use.web_search_requests`,
   priced at $10 per 1,000 searches; the Steps tab shows "Searched the web" and "Found N results" (title — url).
   Gemini's `groundingMetadata.webSearchQueries` become a note. Not done: `pause_turn` (a long server-tool loop) ends
   the reply with a note rather than continuing it; Gemini's grounding fee isn't priced.
6. **Lean prompt for frontier models** (`PromptStyle`; Settings → Generation → System prompt → Working rules:
   Automatic = lean for Claude and Gemini, Detailed, Lean). Lean keeps grounding in what was read, paths, the todo list,
   mode/approval/sandbox rules, and the answer format; drops the coaching small models need (grep first, one file at a
   time, don't repeat calls). Working rules 1,367 bytes against 2,062. The style is part of the frozen prompt's key.
   `kurtkode-eval --prompt-style detailed|lean`; the eval gives Claude and Gemini 16k output and 15 minutes.

## Safety and awareness: permission rules, destructive commands, notifications (2026-10-15, from the opencode study)

1. **Permission rules from settings files** (`Agent/PermissionRules.swift`), in Claude Code's format so its files work:
   `"permissions": {"allow": [...], "ask": [...], "deny": [...]}` with `Bash(git status)` (exact), `Bash(npm run
   test:*)` (leading words), `Bash(git * main)` (wildcards), `Read(./.env)`, `Edit(src/**)`, `//abs`, `~/…`, `mcp__server`
   (`Read` covers every reader, `Edit` every writer; a pattern without a slash matches at any depth, `./` anchors it).
   From `~/.kurtkode/settings.json` and `~/.claude/settings.json` (trusted) and the project's `.kurtkode/` and `.claude/`
   `settings(.local).json`: its deny and ask rules apply at once; its allow rules wait for approval once (a banner in
   the app, a question in the interactive CLI; `permission-approvals.json`, keyed by project and the rules'
   fingerprint). Deny wins over ask over allow, in every mode; deny and ask apply after a PreToolUse hook's allow too.
   An allow rule needs one simple command (no chaining); deny and ask match any part of a chained command.
   **Repeats**: the same call that changes something, made three times in a row, is asked about.
2. **Destructive commands** (`Agent/DangerousCommands.swift`; Settings → Generation → Safety, on by default): git reset
   --hard, clean -f, checkout -- / restore (not --staged), push --force/--delete/+refspec, branch -D, stash drop/clear,
   history rewrites; rm of /, ~, .., the project, or a folder outside the project and temp; sudo, dd of=, mkfs,
   diskutil erase, shutdown; find -delete; a download piped into a shell. Asked about in every mode (Full Auto too),
   never offered "always allow"; a user's allow rule naming the command lets it through. The approval card and the
   CLI say why ("Asking because this command discards uncommitted changes (git reset --hard)"); `kurtkode -p` refuses
   with the reason.
3. **Notifications** (`App/Sources/Model/Notifier.swift`; Settings → Generation → Notifications, on by default): a
   macOS notification when a run finishes, pauses, stops, or waits for approval while kurtkode isn't the front app
   (one per session, replaced by newer); clicking opens the session; showing the session clears it. Debug builds skip
   them with `KURTKODE_NO_NOTIFY=1` (test instances). The CLI rings the terminal bell for an approval and after a run
   over 30 seconds (`notify` setting).
- 279 tests (rules: commands, paths, MCP, precedence, project approval; danger: 16 dangerous and 9 harmless commands;
  the loop: Full Auto asks for git reset --hard, a deny rule blocks without asking, an allow rule runs in Ask mode, three
  identical writes ask). Live on LM Studio Gemma 4 26B (`-p --mode auto`): a project rule denied `cat notes.txt`, `git
  reset --hard` was refused with its reason, the uncommitted change survived. Notifications weren't tried live (the

## Skills and questions to the user (2026-10-15, from the opencode study, #4 and #5)

1. **Agent Skills** (`Agent/Skills.swift`): a folder with a `SKILL.md` (front matter `name`, `description`, then
   instructions), the format Claude Code and opencode share. Found in the project's `.kurtkode/skills`,
   `.claude/skills`, `.agents/skills`, then the same under `~` (the first of a name wins, so a project's skill replaces
   a user's; a folder without a description is skipped; multi-line `description: >` works). Only names and
   descriptions are in the prompt: the `skill` tool's description lists them in `<available_skills>`, so a session's
   prompt grows by one line per skill and the instructions come in when used. Calling `skill` returns the instructions,
   the folder's path, and its other files (up to 40); the skill's folder is added to the run's workspace as a
   read-only extra folder, so its scripts and references can be read (and run by bash) but not changed.
   `disable-model-invocation: true` (or opencode's `autoinvoke: false`) leaves it out of the list but it still loads
   by name. Each skill is also a `/name` command ("Load the skill … and follow it" + what was typed; a custom command
   of the same name wins); `/skills` lists them with their folders. Subagents get the tool unless their tool list
   leaves out `skill`. Claude Code names (`Skill`, `AskUserQuestion`) work in permission rules and hook matchers.
2. **Questions to the user** (`Agent/AskUser.swift`, `ask_user`, read risk): a question with optional options (2–6,
   the recommended first) and `multiple`. Offered only when someone can answer: the app (a blue card under the
   approval card with option buttons, ⌘1–⌘9, checkboxes for `multiple`, a free-text box, Skip; a notification "needs
   your answer"; Stop withdraws it) and the interactive CLI (numbered options; `2`, `1,3`, or words). `-p` runs and
   subagents don't get it; a model that calls it anyway, or a skipped question, is told to decide and say what it
   assumed. Debug builds answer the card by themselves with `KURTKODE_AUTOANSWER=<text or option number>`.

  refusing a write there, an unknown skill; ask_user answered, unavailable, skipped; typed answers).
